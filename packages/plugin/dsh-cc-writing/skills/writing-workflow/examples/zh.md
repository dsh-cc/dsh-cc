# 示例：中文语言修改

这些示例说明本插件的修改风格。每条包含原句、改后句、修改意图和保留含义。
句子为示例原创，不引用他人的文章。

失败模式取自计划 §9：歧义、重复、空过渡、名词化、无依据的因果加强、丢失限定。
最后一例说明应当保持不改的情况。

## 1. 歧义

**原句**：提交延迟的申请会被拒绝，请在截止前处理。

**改后**：在截止时间之后提交的申请会被拒绝，请在截止前提交。

**修改意图**：去掉「提交延迟」的双重读法。它既可指提交时间晚，也可指申请人拖延。

**保留含义**：仍然说明晚提交会被拒绝，仍然要求在截止前完成，没有新增理由或例外。

## 2. 重复

**原句**：该服务在高峰期响应变慢。也就是说，请求多的时候它变慢了。

**改后**：该服务在高峰期响应变慢。

**修改意图**：删除不推进论证的复述。第二句没有带来新信息，只换了说法。

**保留含义**：现象、条件（高峰期）、方向（变慢）都保留；没有补上原因。

## 3. 空过渡

**原句**：综上所述，因此，我们可以看到该方案仍有风险。

**改后**：该方案仍有风险。

**修改意图**：删除三个不承担逻辑作用的过渡词。它们既不引用前文，也不引出结论。

**保留含义**：结论和判断强度不变。风险仍然只是「有」，没有被写成「很大」。

## 4. 名词化

**原句**：我们对日志进行了分析，并完成了对错误原因的定位。

**改后**：我们分析了日志，定位了错误原因。

**修改意图**：把「进行分析」「完成定位」还原为动词，让动作有执行者。

**保留含义**：动作、对象和顺序不变；「错误原因」仍是定位的目标，没有被改成「错误」。

## 5. 无依据的因果加强

**原句**：升级完成后，超时数量下降，说明这次升级解决了超时问题。

**改后**：升级完成后，超时数量下降。现有数据不能证明下降由升级引起。

**修改意图**：把相关写成相关。原文用「说明」把时间顺序升级为因果结论。

**保留含义**：观察到的下降和时间关系都保留；结论的强度降低到证据支持的程度。

**不接受的改法**：只写「超时数量下降」，因为那会丢掉时间关系，读者无法判断证据是什么。

## 6. 丢失限定

**原句**：在并发低于 50 时，该配置一般稳定，我们偶尔会看到重试。

**改后**：并发低于 50 时，该配置一般稳定；偶尔会出现重试。

**修改意图**：缩短句子，同时保留条件和不确定词。

**保留含义**：阈值 50、「低于」、「一般」、「偶尔」全部保留。重试的频率没有被写成从不发生，也没有被写成经常发生。

**不接受的改法**：「该配置稳定」。它删掉了阈值和不确定词，把有限结论变成了普遍结论。

## 7. 保持不改

**原句**：该密钥由运维团队每 90 天轮换一次。

**改后**：该密钥由运维团队每 90 天轮换一次。

**修改意图**：保持原句。这是应当不做修改的情况。

**保留含义**：被动语态在这里指向已知执行者，动作焦点正确；任何改写都可能把「每 90 天」的周期换成「定期」，从而丢掉可核对的事实。在这里改写句子比保留它风险更大。

## 使用说明

- 每个修改只服务一个意图：清晰、简洁或风格。合并意图会让报告无法归因。
- 修改前后要保留数字、引文、术语、条件和判断强度。脚本只能比较其中一部分，
  其余由语义审查判断。
- 这些示例不是文学风格的统一标准。用户给出的明确规则优先于示例和 profile。
