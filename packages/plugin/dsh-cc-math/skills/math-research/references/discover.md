# Discover — discovery loop, evaluator gate and experience store

Operational contract for `evaluator-gate.mjs`, `experience.mjs` and the M3 rows
of `claim-ledger.mjs` (design §6.1 loop, §6.2 gate, §6.3 claim table, §7.2
experience store, §8.3 ablation). Read this before the first generation.

## Loop

Manifest `discovery` carries everything: `{selectionK, convergenceG, rngSeed,
populationSize, programLanguage, evaluatorSignature}`; `trustedExamples` pins
the examples as `{problemId, source, sha256}`. There is no ambient setting and
no settings flag: a missing field means the loop does not start.

```
1. select parents       — seeded: top-K by score + K random          (evaluator-gate select)
2. mutate programs      — the model's job, not the harness's
3. evaluator gate       — failing individuals are discarded, never scored
4. scored insertion     — snapshot written, claims generated          (evaluator-gate snapshot)
5. terminal             — budget exhausted, or no improvement for convergenceG generations
```

Population snapshots are `population/gen-<n>.json`:

```json
{ "schemaVersion": 1, "rngState": 1747213921,
  "individuals": [{ "id": "i-3", "program": "…", "score": 0.71,
                    "evaluatorVersion": "<sha256>", "parentIds": ["i-1"] }] }
```

`rngState` is recorded so a resume continues the same stream. **Selection is
reproducible** — `selectParents(population, K, rngState)` is a pure function
(top-K by score with id tie-break, then K drawn without replacement with an
xorshift32 stream) returning both the parent ids and the advanced `rngState`.
The *programs* are model-generated and are **not** bit-reproducible: report the
selection as reproducible and the mutation as not, never the other way round.

```
evaluator-gate.mjs select   --run <run> --generation 3 --k 4
evaluator-gate.mjs show     --run <run> --generation 3
evaluator-gate.mjs snapshot --run <run> --generation 4 --individuals <file>
```

## Evaluator gate (§6.2)

```
evaluator-gate.mjs gate --run <run-dir> --evaluator <program> --checker <independent-program> \
                        [--examples <dir>] [--timeout-ms 60000]
```

1. **Trusted examples first.** They are supplied before the loop (user-supplied
   or literature-known), never generated by the evaluator's own pass. Each is
   re-hashed against the manifest's `sha256`; a swapped example aborts the run
   (`evidence-mismatch`) rather than being scored. The evaluator must pass
   **every** one. Both programs are invoked as `<program> <case.json>` and pass
   a case by exiting 0.
2. **Double implementation.** An independently generated checker must agree with
   the evaluator case by case. Any disagreement — or a checker that did not run
   — fails the gate.
3. **Version pinning.** The gate record carries `bindingHashes: {evaluator,
   checker}` (sha256 of each program file). Claims cite that version; changing
   the evaluator mints a new version and moves affected claims to
   `revalidation-pending`.
4. **Correlated-mistake caveat.** Two model-generated implementations agreeing
   is *weak evidence, not proof*. Say so in every report that relies on it.
5. **Feasibility vs. score.** That a program runs (feasibility) is not a score
   (that it achieves something). Report them separately, always.

Failing (1) or (2) exits 1: the gate is a rejection, never a pass with a
warning. There is no override flag.

## Experience store (§7.2)

```
experience.mjs query       --query "<goal shape>" [--kind success|failure] [--top 20]
experience.mjs add-success --record <record.json>
experience.mjs add-failure --record <record.json>
experience.mjs verify | status
experience.mjs block --reason "ablation <config>"   |   experience.mjs unblock
```

- **Success store** — `{goalShape, premises[], tacticSkeleton, sourceProblem,
  verifiedAt, bindingHashes, verification}`. `verification` must be
  `{kind:"formal-proof-valid", verdict:"pass"}`; anything else is refused with
  exit 2. Pollution here poisons every later search, so the gate is the point.
- **Failure store** — `{goalShape, failedApproach, errorClass}`. Consulted
  BEFORE generation: it saves a doomed attempt, and it makes no correctness
  claim.
- Append-only `experience.jsonl`, chain-hashed exactly like `claims.jsonl` (any
  field edit breaks `verify`). Retrieval is FTS5 over goal shape, premises,
  tactic skeleton and error class.
- Single writer through `.lock`: stale after 60s, fail-closed on conflict.
- **Ablation write-blocking** (§8.3): a run marks the store with
  `writeBlocked` (or passes `--write-blocked`, or sets
  `MATH_EXPERIENCE_WRITE_BLOCKED=1`). Test-split writes are then refused until
  `unblock`. A write-block never expires by age — refusing the write is the safe
  failure.

Routing (honest v1 semantics): an experience hit routes the attempt to the
cheap lane (the existing executor subagent); a miss, or a failed first repair
round, routes to the strong lane (the main conversation). That is a delegation
choice, not a runtime mechanism, and it invents no alias.

## Claim statuses in M3 (§6.3)

| edge | condition |
| --- | --- |
| `open → experiment-supported` | `experiment` record: `evaluatorVersion` (sha256) + `snapshotRef` |
| `experiment-supported → proven` | **exactly** `open → proven`: L2 pass + `anchored`/`human-confirmed` fidelity + no outstanding full-isolation L1 counterexample |
| `any non-terminal → revalidation-pending` | `evaluator-change` record (the entry records `priorState`) |
| `revalidation-pending → prior state` | `revalidation` verdict `passed` — and only the state it left |
| `revalidation-pending → superseded` | `revalidation` verdict `failed` |
| `experiment-supported → superseded` | fidelity correction **or** failed revalidation |

`model-assessed` fidelity never promotes an experiment-supported result: there
is no weaker path to `proven`. Terminal `superseded` and `fidelity-failed` are
never re-sources, so they can never be parked for revalidation.

## Report

Every reported discovery result states: the evaluator version, the snapshot it
came from, whether the gate passed, the double-implementation outcome, and the
caveat above. A result without a passing gate is not a result — it is a
candidate that did not clear the bar, and it is reported as such.
