## 1. Context

dsh-cc consumes ~64 `@deepseek-ai/*` packages through `link:` devDependencies
and `>=0.1.1-rc.2` peer ranges. Five breaking surface changes must be absorbed:

1. **`packages/client/runtime` removed** (be531688f3). Consumer:
   `packages/interaction/command-permissions` imports `ClientContext`,
   `ISessions`, `SessionFace` from `@deepseek-ai/dsh-client-runtime/client`.
   Replacements verified at the pin: `ClientContext` = cordis `Context`;
   `ISessions`/`SessionFace` live in `@deepseek-ai/dsh-api-session-controller/client`.
2. **`packages/subagent/tool-subagent-report` removed with no replacement**
   (merge b91e7ce366; preceded by ec493c2db8 steer-unification). Consumers:
   `packages/bundle/cc-shell`, `packages/subagent/task` (links + composition
   tests), `packages/subagent/coordinator` (doc/prompt contract).
3. **Value utilities extracted to NEW package `@deepseek-ai/dsh-util-values`**
   (`packages/util/values`, 0.1.3-alpha.2): `JsonValue`, `isJsonValue`,
   `snapshotJsonValue`, `deepFreeze`, `assertNever`, `deepEqualJson`. `dsh-llm`
   and `dsh-session` no longer re-export them.
4. **`CallId` renamed to `ToolCallId`** in `dsh-llm` (a789637db6; constructor now
   uses `brandString` instead of identity cast). Ripples into dsh-cc's own
   `ToolExecution.callId` type — a dsh-cc public-type change.
5. **Pure helper exports removed:**
   - `dsh-settings`: `settingsNamespace()`, `installSettingsSection()` → type-level
     constraint (`SettingsNamespaceInput`) + `SettingsProvider.installSection()`
     method (index.ts:472). `SettingsNamespace` type and `SettingsSectionHooks`
     still exported. persist/publish/watcher contract otherwise unchanged
     (settings hot-reload safe; treated as unverified-by-reviewer, smoke-tested).
   - `dsh-plan-mode`: `foldPlanMode()` → session projection `plan`.
   - `dsh-sandbox-policy`: `effectiveSandboxMode()` → projection `sandboxMode`;
     `setSandboxMode`/`SANDBOX_MODES` unchanged (session-mode.ts exports both
     at the pin).

Also: `cc-serena-first/package.json` links the never-existent
`packages/agent/agent` (broken even at baseline) → fix to `packages/core/agent`.

Non-goals: adopting upstream web/sidebar features; re-plumbing dsh-cc onto
upstream projections for reads dsh-cc already folds (see §5 rationale); any
harness checkout source modification (read-only directive — `pnpm build:lib`
writes only gitignored `lib/`, verified `.gitignore:4`, allowed).

### S5 — report-tool removal & delivery redesign (design-bearing)

- `SubagentRuntime.followup` is REMOVED. Public model-facing delivery is
  `sendMessage(sender, targetId, content, {signal})` — STEER semantics

  absent ones). Queue delivery (`queuePrompt`) is private behind the

## Retarget to 0.1.2-rc.1 (2026-09-12)

### Why

The default install path — `npm install -g @deepseek-ai/dsh` — resolves its
`latest` dist-tag to **0.1.2-rc.1**; 0.1.3-alpha.2 is reachable only through
the alpha dist-tag. dsh-cc must support the channel users get by default, so
the retarget moved the harness baseline from 0.1.3-alpha.2 back to the rc.1
release commit. (Upstream per-package `latest` tags are incoherent —
`dsh-util-values` latest = 0.1.2-alpha.2, `dsh-agent` latest = 0.1.0-rc.6 — so
the meta package's `latest` is the only meaningful version anchor.)

### What changed

- Harness pin → `a66e4702` (0.1.2-rc.1 release commit); all `@deepseek-ai/*`
  peer floors → `>=0.1.2-rc.1`; launcher `MIN_DSH_VERSION` gate enforces the
  floor at bootstrap (version-gate test matrix in
  `packages/launcher/tui/tests/version-gate.spec.ts`).
- RC-1: rc.1's AgentLoop requires a hard `sessionProjections` inject that the
  rc.1 testkit does not mount — dsh-cc test compositions now mount
  `SessionProjectionRegistry` before AgentLoop.
- RC-2: rc.1 accepts only session-header version 0 (with a mandatory
  `isSeeded` boolean) — fixtures re-versioned from the alpha.2 v2 shape.
- RC-3: rc.1's persistence face is `readStoredRevision(id)` (not `stat`), and
  the resume-pins gate plus its tests were adapted; the alpha.2 per-session
  read-handle face (`open/stat/flush`) is gone.
- Also absorbed: `AgentLoop.create` is synchronous at rc.1 (alpha.2 was async),
  and the system-prompt persona knob is `persona` (not `personaPrefix`).

### Semver floor semantics (decision)

node-semver's prerelease-tuple rule means `>=0.1.2-rc.1` does **not** admit
`0.1.3-alpha.2` (nor `0.1.2-alpha.5` — correctly, since alpha sorts below rc).
Alpha-channel harness users must use the matching dsh-cc channel.
**Accepted** and pinned by the launcher gate test matrix.

### Install mechanics (verified statically at rc.1 + live)

`dsh plugin add` is a thin pnpm forwarder; the profile pnpm-workspace sets
`autoInstallPeers: false` + `nodeLinker: hoisted` (harness
`profile.ts:182-187`), and runtime `@deepseek-ai/*` resolution heals to the
HOST installation through symlinks under `$DSH_HOME/profiles/node_modules`
(`profile.ts:497-532, 579-605`). Conclusion: peer floors are advisory
metadata; the **host dsh version is the real compatibility surface** — hence
the launcher gate. No dual-copy risk for peer-declared packages.

### Exception: web/fetch-http regular dependency

`packages/web/fetch-http` declares `@deepseek-ai/dsh-web-fetch-http` as a
**regular** dependency — load-bearing, because the host dsh installation
closure does NOT contain that package (verified: absent from the ~204 fallback
symlinks in the profile), so a peer declaration would not resolve; pnpm
installs it into the profile from the registry. Constraint: `^0.1.2-rc.1` on
0.x is minor-locked (<0.1.3) — every harness minor bump requires a manifest
edit here.

### Open-range policy

Peer floors stay open-ended (no upper bound); CI pins the floor. Forward
compatibility with future harness releases is verified at pin-bump time via
the existing `DSH_HARNESS_REF` workflow. Follow-up candidates (recorded, NOT
implemented): weekly canary CI against upstream `latest`; a doctor-command
harness-version surface (docs/plans/2026-09-04-doctor-health-report.md
anticipated `ctx.harnessVersion`).

### v0.5.0 cohort

Users on dsh-cc v0.5.0 (floors `>=0.1.1-rc.2`) with today's default dsh
install (0.1.2-rc.1) are already broken. The next dsh-cc release notes must
say: **"dsh >= 0.1.2-rc.1 requires dsh-cc >= this release; upgrade both
together."**
