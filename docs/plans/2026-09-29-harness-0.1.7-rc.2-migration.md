# Harness 0.1.7-rc.2 Migration

Status: **Approved (user sign-off 2026-09-29) — grok rounds 1–3 GWA all folded (round 3 refinement-level), codex seat closed by explicit user decision after three contamination failures (reduced roster: grok + internal critic fold-check PASS-WITH-NITS); Option A settings fork explicitly confirmed by the user. Implemented — stacked PR chain #172/#173/#174/#176 (all merged 2026-09-30); see §5 for the slice plan.**
Date: 2026-09-29
Scope: dsh-cc retarget from harness 0.1.5-rc.1 (pin `1ef9c1fa9a`) to 0.1.7-rc.2 (release commit `787b746b80`, npm `latest`). Touches nearly every package that consumes `@deepseek-ai/*` APIs; the deepest reworks are the message-model migration (session format v4) and the settings provider decoupling.

## 1. Problem

`npm install -g @deepseek-ai/dsh` now resolves `latest = 0.1.7-rc.2`, and the sibling
deepseek-harness checkout is aligned to `787b746b80` with a fresh `build:lib`. dsh-cc
still pins 0.1.5-rc.1 in `.github/workflows/presubmit.yml` (`DSH_HARNESS_REF`) and
every `package.json` floor is `>=0.1.5-rc.1`. The full 0.1.5-rc.1 → 0.1.7-rc.2 span is
3,654 commits; a forced `tsc -b tsconfig.packages.json --force` against the 0.1.7-rc.2
sibling build yields **76 type errors across ~30 files**, plus a set of runtime /
config-schema breaks that no type check covers. This document inventories the
verified incompatibilities, resolves the open design questions, and lays out the
migration slices.

## 2. Ground truth (verified against the harness checkout at `787b746b80`, old side at `1ef9c1fa9a`)

- **G1. Session format v3 → v4.** `SESSION_FORMAT_VERSION` is 3 at the old pin
  (`packages/core/session/src/types.ts:88` at `1ef9c1fa9a`) and 4 at 0.1.7-rc.2. A
  dedicated migration chain exists (`packages/session/session-format-v3-to-v4/`); the
  persistence layer refuses both newer and older versions with distinct errors, so
  reads of stored v3 logs go through migration.
- **G2. Role-keyed message model.** `MessageRoleMap` (system / developer / user /
  assistant / tool) is closed. `ToolResultBlock` no longer exists in `@deepseek-ai/dsh-llm`;
  tool results are first-class `ToolResultMessage` (`role: 'tool'`, `toolCallId`,
  `isError`) — `packages/llm/llm/src/message.ts` (ToolResultMessage interface).
  On disk (v4), the `type:'tool-result'` wrapper is removed: `data.message.role`
  becomes `'tool'`, `toolCallId`/`content`/`isError` move from the wrapper to the
  message (`packages/session/session-format-v3-to-v4/README.md:85-96`).
- **G3. `MessageSource` has no catch-all `plugin` kind.** The union is
  merge-extensible per producer (`packages/llm/llm/src/message.ts:107-116`):
  the base map has only `user`, `model`, `tool`, `system-prompt`; named kinds
  exist as module augmentations in the producers that own them
  (`compact-checkpoint`, `ptc-mode`, `tool-registry`, `agent-message`,
  `subagent-settled`, `skill-invocation`, `user-approval`, …). A runtime
  `plugin:<name>` kind does **not** exist at 0.1.7-rc.2 — that spelling is a
  v4 on-disk migration artifact only — so dsh-cc producers must declare
  their own named kinds via `declare module`, not invent `plugin:…`.
  Old dsh-cc code writing `{ kind: 'plugin', plugin: '<x>' }` fails to compile at
  ~15 sites.
- **G4. `Message` vs `RequestMessage` split.** `resolvedOptions.messages` in the llm
  service is now `readonly RequestMessage[]` (assembler projection change).
- **G5. Settings service rebuilt.** `SettingsProvider` (abstract `load()`/`persist()`/
  `installSection()`, emitting `settings/updated(ns, next, prev, source)` — old
  `packages/settings/settings/src/index.ts:333-472` at `1ef9c1fa9a`) is **deleted**.
  The new `ctx.settings` is `SettingsForms` — a concrete Service over cordis profile
  patch documents: `describe()`, `update(ns, patch, expectedRevision)`, `replace()`,
  `mutate()`, `configure()`; edits are restricted to **volatile** fields of active
  plugin entries; the event is `settings/document-updated(ns, revision)`; a legacy
  `settings.yaml` is auto-imported into the profile once
  (`packages/settings/settings/src/index.ts:223-431`).
- **G6. Agent events.** `agent/session-start` is removed; `source` (and an optional
  `signal`) moved onto `agent/created`, whose listener may now return a promise.
  `AgentRegistry.announce(agent, source, signal?)` is async with a new required
  `source` parameter. `AgentRegistry.register` now returns the effect disposer.
- **G7. AgentLoop config.** `AGENT_LOOP_SETTINGS_NAMESPACE` / `AgentLoopSettings` /
  `AGENT_LOOP_SETTINGS_SCHEMA` exports are gone; `Config.maxParallelToolCalls` is
  now a **required** `Volatile<number>` (`.volatile()` schema field). Public
  `AgentLoop.config` exposes `Config`, not a resolved snapshot.
- **G8. Subagent surface.** `SubagentRuntime` constructor takes `(ctx, config)` with
  `maxActiveSubagents`/`maxDepth` as `Volatile<number>`; `listChildren` returns
  `SubagentCatalogEntry[]` — **not a type rename but a shape change** (see
  Slice 3); `remoteExportList` and `SubagentCatalog` are removed.
  `tool-subagent`'s `Config.maxDepth` lost its schema default (was 3); the
  effective default now resolves per delegation via `resolveMaxDepth()` and is
  documented as **1** unless configured — dsh-cc's task tool already pins 3.
  `@deepseek-ai/dsh-agent` now declares a type-level dependency on
  `@deepseek-ai/dsh-workspace`.
- **G9. Shell executor.** `ShellExecutor.run()` is gone; the contract is now
  `resolve(request: ShellExecRequest): ShellExecSpec` + `execute(spec): Promise<ShellExecution>`
  (`packages/shell/shell/src/index.ts:64-93`).
- **G10. Jobs.** `JobSnapshot` is no longer exported (replaced by the `JobView` /
  `JobRead` family) and `JobRegistry.onJobsChanged` is removed. The listening idiom
  is `ctx.jobs.events.subscribe(filter, listener)` where
  `filter: { owner: SessionId } | { owners: 'all' | 'scope' }`
  (`packages/jobs/jobs/src/types.ts:230-253`); events are dispatched synchronously
  after the commit they announce (`registered`, `settled`, output ring events).
- **G11. PreToolDecision.** Old union `{allow} | {deny; reason} | {ask; reason?}` →
  new `{allow} | {deny; reason; info?: ToolErrorInfo} | {cancel} | {ask; reason?;
  displayReason?: {en, [locale]: string}}` (`packages/core/tools/src/index.ts:607`).
  `cancel` selects the canonical cancellation result without presenting a policy
  denial; `ask` semantics now run only after an approval service returns
  `allowed-once`.
- **G12. PTC runtime rename (not a floor bump).** The old
  `@deepseek-ai/dsh-code-runtime` package was deleted and replaced by
  `@deepseek-ai/dsh-ptc-runtime` (+ node impl) in harness release
  `7c9bb5914c refactor(ptc)`. The service is now `ctx.ptcRuntime`. **dsh-cc
  forks the harness tools package** (`packages/core/tools` = `@dsh-cc/tools`,
  mounted as `tools-cc` via `packages/bundle/cc-shell/cordis.patch.yml`); the
  fork still imports `CodeRuntime` from the deleted package and links the
  removed directory (`package.json:37,52`). This is a substantive port
  (`CodeRuntime` → `PtcRuntime`, `ctx.codeRuntime` → `ctx.ptcRuntime`), not a
  dependency edit — the original TS2307 ×5 diagnosis missed the fork entirely.
- **G15. Agent-preset architecture replacement.** `packages/preset/
  agent-presets` (`@deepseek-ai/dsh-agent-presets`) was deleted upstream and
  replaced by `@deepseek-ai/dsh-agent-preset-registry` +
  `@deepseek-ai/dsh-agent-preset`. dsh-cc's cc-tui patch still mounts the
  removed package (`packages/bundle/cc-tui/cordis.patch.yml:86-87`), and the
  composition drift gate searches for the obsolete path and **silently skips
  when absent** (`packages/preset/cc/tests/composition.spec.ts:43,126`) —
  a production boot break plus a disabled safety check.
- **G16. Base-bundle `settings.configure` consumers.** Harness base-bundle
  rows active under every profile — `agent-default-model`
  (`packages/core/agent-default-model/src/index.ts:60`), `permission-presets`
  (`packages/interaction/permission-presets/src/index.ts:210`, base row at
  `packages/bundle/base/cordis.patch.yml:249`), `llm-deepseek`
  (`src/host.ts:21`), and `llm-pi-ai` (`src/index.ts:150`) — call
  `configure()` on `ctx.settings`. dsh-cc's cascade replaces that service at
  the same key, and the vendored 0.1.5 contract has no `configure()`: without
  a compatibility facade, boot reaches an undefined method. The new
  agent-preset registry calls it too
  (`packages/preset/agent-preset-registry/src/index.ts:63`). These callers
  only register presentation policy, so the no-op facade covers them — but
  the deeper behavior gap is the Q3 namespace disposition matrix (rc.2
  consumers read their own Config, not namespaces).
- **G13. Mostly unchanged tooling — with one exception.** `engines.node`
  (`^22.19.0 || >=24.0.0`), pnpm 11.7.0, and vendored cordis (4.0.2 → 4.0.4,
  minor) are unchanged; **but the preset-tier layout is not** (G15:
  agent-presets deleted/replaced). No CI toolchain impact beyond the ref pin
  and the pnpm-workspace exclude audit.
- **G14. Type-level break inventory.** Forced `tsc -b --force` against the 0.1.7-rc.2
  build: 76 errors, top clusters: settings-cascade (12), compaction-micro (5),
  cc-shell (4), tool-git-worktree (5 across 4 files), hooks-claude-code (9 across
  4 files), settings-ns (3), plus one-off sites in permission-rules, context-crusher,
  edit-recovery-hint, command-diff, command-tasks, side-query, reasoning-fold,

## 4. Resolved design questions

### Q1 — PreToolDecision new shape (G11)

The union gains `cancel` and `deny.info`; `ask` gains `displayReason`.
**Important correction from external review:** dsh-cc executes decisions in
its own forked tool runtime (`@dsh-cc/tools`), whose local
`PreToolDecision` (`tool-types.ts:301`) still has the old three-member union
and whose executor assumes every non-allow decision carries `reason`
(`runtime-execute.ts:181-183` — `decision.kind === 'allow' ? guardReason :
decision.reason`; a `cancel` has no `reason`, so `denialReason` is
`undefined` and **the tool dispatches anyway**). The migration therefore has
three layers, not one:

1. **`@dsh-cc/tools` fork**: extend the local `PreToolDecision` union
   (`cancel`, `deny.info`, `ask.displayReason`), and port the harness
   executor's `cancel` branch (`if (decision.kind === 'cancel') →
   toolAbortedBeforeDispatchResult()` before dispatch, harness
   `packages/core/tools/src/index.ts:1516-1518`). Add `deny.info` with its
   contract: `ToolErrorInfo` requires stable `name` and `code`, and `reason`
   is explicitly **not model-facing** — populate from structured error
   identity, never free-form stderr.
2. **Bridge fold (`register-events.ts`)**: hooks can never emit `cancel`
   (the CC codec is `allow|deny|ask` only, `hook-protocol/src/codec.ts:42`);
   `cancel` arises **downstream only**. The fold table (test it where the
   fold lives — `hooks-claude-code` — plus the fork's own executor tests):

   | hook \ downstream | allow | ask | deny | cancel |
   |---|---|---|---|---|
   | (none) | allow | ask | deny | cancel |
   | allow | allow | allow | deny | cancel |
   | ask | ask | ask | deny | cancel |
   | deny | deny | deny | deny | deny |

   A downstream `cancel` must return before hook ask/allow folding so an
   external allower cannot resurrect a cancelled execution; downstream
   `deny` always wins. `deny.info`/`ask.displayReason` pass through when
   their side wins.
3. **Fork runtime contract beyond the union** (external review): port the
   optional denial reason/info (`tools/src/index.ts:489`), denial info
   embedded into results (`:1519`), and `ask.displayReason` forwarded into
   approval requests (`:1749`) — the fork's `abort-utils.ts:20`,
   `runtime-code.ts:106`, `runtime-execute.ts:181` lack these paths today.
4. **Capability manifest**: CC has no `cancel` counterpart — document it as
   a deviation row (deny-with-different-user-text), not a codec
   `permissionDecision` value.

Note on `ask` semantics: routing `ask` through the approval service
(`allowed-once` gate) is **not new** in 0.1.7 — the 0.1.5 union already
documented it. The R1 end-to-end probe stays because `cancel` and
`displayReason` are new inputs to the same path.

### Q2 — Jobs listening idiom (G10)

`onJobsChanged(callback)` → `ctx.jobs.events.subscribe(filter, listener)`
with `filter: { owner: SessionId } | { owners: 'all' | 'scope' }`. Consumer
inventory correction (external review):

- **`command-tasks` (/tasks)** does not subscribe at all — it only calls
  `list()`. Its migration is `JobSnapshot` → `JobView` plus
  `list(agent.sessionId)` (the parameter changed `Agent` → `SessionId`).
- The **only production `onJobsChanged` consumer is the TaskCreated hook
  bridge** (`hooks-claude-code/src/register-events.ts:307-323`): it primes
  `jobs.list(undefined)`, diffs on change, and lists per owner. Its
  subscription policy must be chosen explicitly: `{ owner }` also delivers
  **unowned** jobs, while `{ owners: 'scope' }` isolates composed owners —
  the preset-scoped mount wants `{ owners: 'scope' }`, dispatching only
  `registered` events. Hook fakes/tests follow.

### Q3 — Settings-cascade feasibility (G5)

The new harness settings model (profile-patch volatile-field forms) and dsh-cc's
Claude-Code settings.json cascade are **different products**: the dsh-cc cascade is
a CC-parity surface (five JSON layers, write-through user layer, chokidar hot
reload, `settings/updated(ns, next, prev, source)` semantics, CC key aliases) and
must not be re-pointed at profile yml patches. Decision — **Option A: decouple**:

1. Vendor the old `SettingsProvider` contract into dsh-cc as a new package
   `@dsh-cc/settings-provider`. **Vendor the whole 0.1.5 settings module
   surface that dsh-cc actually imports — enumerate from imports, not from a
   guessed line budget** (the class alone is ~523 lines at
   `1ef9c1fa9a:packages/settings/settings/src/index.ts:333-855`, and
   `SettingsWatcher`/`SettingsRegistration`/`parseSettingsNamespace` were
   never exported there; `settingsNamespace` does not exist on the old pin
   at all — the `command-config.spec.ts:8` import is dead code to fix in
   passing). Slice 1 starts with `git grep` of every
   `@deepseek-ai/dsh-settings` import across src **and tests**, and the
   vendored surface is that list, closed under internal references.
2. `SettingsCascadeProvider` extends the vendored base instead of the harness
   class; its `load()`/`persist()`/watchers/hot-reload machinery is untouched.
3. All dsh-cc consumers keep `installSection`/`settings/updated` unchanged — the
   migration cost collapses to the cascade package + the vendored base.
4. **Compatibility facade for `configure()` (G16, external review):** harness
   base rows (`agent-default-model`, `permission-presets`) and the new
   agent-preset registry call `ctx.settings.configure({auto}, fiber)` at boot.
   The vendored contract must expose a **no-op `configure()`** (returns a
   disposer; logs once at debug) so those rows boot; the intentional
   semantic gap — dsh-cc settings are the CC JSON cascade, not profile-patch
   forms, so "presentation policy" is meaningless — is documented and
   covered by a boot-time test that mounts `agent-default-model` against the
   cascade. "Exactly one provider is live" remains necessary but is not
   sufficient; the facade is.
5. Service binding: dsh-cc mounts the cascade as `ctx.settings` today via
   `packages/bundle/cc-permissions/cordis.patch.yml`. Keep dsh-cc's
   composition free of the harness `settings/settings` package (duplicate
   `ctx.settings` is a hard cordis collision) and add a composition smoke
   assertion that exactly one `ctx.settings` provider is live **and** that
   `typeof ctx.settings.configure === 'function'`.
6. Anything harness-side that later *requires* the fuller `SettingsForms`
   API (beyond `configure()`) becomes an integration item at that time —
   flagged as a known risk, not solved speculatively.

**Namespace disposition matrix (Q3 addendum — external review blocker).**
Vendoring the contract plus a no-op `configure()` keeps the process booting,
but **rc.2 harness consumers read their own cordis Config, not settings
namespaces** — dsh-cc writes into the vendored provider would silently stop
affecting routing. Each cross-boundary namespace needs an explicit
disposition:

- `llm-pi-ai` (providers): dsh-cc's /provider UI reads it
  (`tui/src/provider-read.ts:16-49`, via the inherited `describe()` and the
  descriptor's `user.providers`) and writes it
  (`tui/src/provider-settings.ts:43-50`, via the inherited
  `mutate('llm-pi-ai', pathOps, revision)`). At rc.2 the adapter resolves
  profiles from its own entry Config (`llm-pi-ai/src/index.ts:148-164`)
  and the default model persists via `configEditor.edit`
  (`agent-default-model/src/index.ts:82-91`). Disposition — **bridge with
  data migration**: (a) the vendored provider keeps `describe`/`mutate`/
  `replace` (the cascade's own tests call them); (b) a one-shot copy moves
  the existing `llm-pi-ai` and `agent-default-model` sections of the user
  `settings.json` into the live plugin entries before the new write path is
  used — a forward-only `configEditor` bridge would leave those sections
  unread (boot green, routes silently gone); (c) the TUI write path switches
  to `mutate`-equivalent path ops against the plugin entry config (plus
  `replace` for the default model, or `agentDefaultModel.saveSelection`);
  `configEditor.edit` is a raw rewrite with no revision token and no
  volatile-path check, so those guards live in the bridge; (d) keep reading
  the user override, not the fully resolved config.
- `agent-loop` settings namespace: **removed** upstream entirely
  (`AGENT_LOOP_SETTINGS_*` deleted) — no disposition needed beyond Slice 3.
- Remaining old-pin `installSection` consumers (permission-presets,
  llm-deepseek, bash/pwsh-local, subagent model-selection, web-search —
  enumerate with `git grep 'settings\.installSection' 1ef9c1fa9a -- packages`):
  disposition per namespace at Slice 1 time — **bridge** where dsh-cc UI
  reaches it, **fork** where behavior diverges, or **removed** where the
  dsh-cc surface intentionally does not use it. The matrix is closed in the
  Slice 1 commit, not mid-migration.

Option B (bridge onto SettingsForms) is rejected: it would move CC-parity
settings into profile yml patches, break the five-layer merge and hot-reload
semantics, and put CC `settings.json` files through an auto-import shim —
strictly worse for parity.

## 5. Migration plan (slices, order, files)

**Stacking and CI shape (explicit — supersedes any looser reading).**
External review falsified the intermediate-red-merge idea: `main`'s ruleset
(22367074) has PR + linear-history rules and **no required status checks**,
no expected-red label, no merge queue, and the local pre-commit hook runs
typecheck + tests on every commit. A red-PR accommodation does not exist, and
red intermediate merges onto `main` are not house practice. Therefore: **one
PR, slices as commits (working checkpoints), pin moves in the first commit,
and only the final state must be green**. (The alternative — keeping the old
pin until the end — does not work: later slices reference types
(`ToolResultMessage`, `agent/created`) absent at the old pin.) The local
pre-commit hook (`.husky/pre-commit` runs typecheck + tests on every commit)
blocks red checkpoint commits, so the procedure is explicit: **slice commits
0–4 carry a time-boxed, commit-message-recorded `--no-verify` waiver;
the final commit passes the full hook, and the merged PR is green.**
(Alternative if the waiver is rejected: develop uncommitted until the
series is green, then split with an interactive rebase from the green tree.)
