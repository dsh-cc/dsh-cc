# VWA Post-lane-2 Fix Batch — Fix 3: Review Settings Revision (capacity-only, cache-preserving)

## Status: Implemented — PR #278 (open, pending merge). Three-lane blind review converged (r1 full review: NO-GO on all seats → v2 redesign; r2 delta confirmation; r3 micro-confirmation — final round GO on all seats).

All anchors cite tree `b64af0e8`, verified 2026-10-21. Stacks on Fix 1 + Fix 2.

## 1. Problem

Review settings (`FrozenReviewSettings`: the budget object,
`maxArtifactChars`, `maxContextChars`, `claimsBatchSize`) are frozen into
`contract.reviewSettings` at init (store.ts:202-215, review-config.ts:11-28)
and never revisable:

- Changing settings.json has no effect on existing projects.
- The only documented escalation is the refusal's option (c): create a new
  project — which silently discards every registered source, evidence item,
  claim, and completed review record.
- The freeze exists for good reason — review records are keyed by their
  inputs (§A.2 identity) — but the current implementation hashes the ENTIRE
  contract (including `reviewSettings`) into every identity surface, so even
  a pure capacity change (a budget number no completed record depends on)
  invalidates all reuse.

User adjudication (2026-10-21, selected option B): revision must preserve
completed-record reuse; capacity fields are stripped from record identity.

## 2. Design

### F3.1 One identity policy: the semantic contract hash, everywhere

The v1 draft proposed switching "four enumerated sites"; r1 review (all
three seats) proved the inventory incomplete. The complete set of surfaces
that today compute or compare the full-contract hash:

**Production sites** (hashes folded into new records):
- `cacheKey` (review-continue.ts:136-145) — every semantic record's
  `inputHash`.
- `auditInputHash` (audit-reuse.ts:33-56) — audit records.
- `auditDependencyDigest` (review-current.ts:119-141) — hashes
  `contract: snapshot.contract` **including reviewSettings** inside the
  audit dependency digest.
- `errorRecord` (review-runner.ts:181-216) — `contractHash` field.
- `argument.review` admission (tools.ts:~396 and tools.ts:444 — two
  top-level computations passed to feasibility and runner deps).

**Comparison sites** (match stored records against a recomputed hash):
- `currentReviews` / `matchesReviewTask` (review-current.ts:46, 11-28) —
  requires `r.contractHash ===` recomputed hash AND recomputes `cacheKey`
  with it; the load-bearing currentness filter.
- `semanticRecordHash` / `taskDependencyDigest` (review-input.ts:41-75) —
  record content hashes chained into downstream digests.
- `review-progress.ts:76, 140` — progress currentness.
- `delivery-check.ts:161, 168` — delivery audit selection.
- `activeAdjudications` digest (delivery-check.ts:44-58) — embeds the full
  contract.
- `executeReviewRun`'s end-of-run freshness compare (review-runner.ts:443-481)
  — compares `stableJson({contract: snapshot.contract, ...})` before/after.

**The policy**: one `semanticContract(contract)` view (the contract object
minus the `reviewSettings` key) and one `semanticContractHash(contract)`
exported from review-contract.ts. EVERY site above switches to it —
production sites write it, comparison sites recompute it,
`auditDependencyDigest` hashes the semantic view of the contract, the
end-of-run freshness compare uses the semantic view, and
`activeAdjudications` uses the semantic digest. Where records are matched
against recomputed keys, a single shared helper (e.g.
`recordMatchesKey(record, key)`) is used by continue planning, the runner,
`collectCachedRecords`, `hasReusableAudit`/`findReusableAudit`, and
`matchesReviewTask` — no site-specific matching logic. The site list is
regenerated by grep (`contractHash`, `stableJson(snapshot.contract`,
`stableJson(...contract`) at implementation time and pinned by the F3.5
end-to-end test.

### F3.2 Migration: no probing, one disclosed invalidation

The v1 dual-probe (miss on the semantic key, retry with the legacy
full-contract key) is **dropped** — r1 established it cannot work:

- The legacy hash includes the write-time `reviewSettings`; after a
  revision the recomputed legacy hash differs, so pre-upgrade records miss
  both keys on exactly the user journey this fix exists for.
- Identity chains recursively: `semanticRecordHash` includes
  `contractHash` + `inputHash`, and `taskDependencyDigest` hashes upstream
  record hashes — patching stored keys without a topological rewrite breaks
  downstream identity, and rewriting is unsound for the same reason.

The contract going forward: **records written after this change survive any
settings revision** (identity omits `reviewSettings`). Records written
before the change are invalidated **once at upgrade** — their keys were
computed with the full-contract hash and no longer match. This is disclosed
in the PR description and the revision response; the cost is one
re-execution per existing project (money, not correctness). No record
rewriting, no probing, no key versioning.

### F3.3 The revision operation: `set-review-settings` mutation op

New mutation op on the existing `argument.update` pipeline (tools.ts:261-270,
graph.ts):

```jsonc
{
  "op": "set-review-settings",
  "reviewSettings": {
    "budget": { /* any subset of the 7 ReviewBudget fields, explicitly provided only */ },
    "claimsBatchSize": 2,
    "maxArtifactChars": 240000
  }
}
```

- **VALID_OPS** (graph.ts:161) gains the op, and `applyMutation` gets an
  explicit branch **before** the bind-artifact `else` fallthrough
  (graph.ts:212-214 — without a branch the op would fall through and
  corrupt). The `Mutation` union (graph.ts:37-47) is extended.
- **Allowed fields**: the seven `ReviewBudget` fields, `claimsBatchSize`,
  and `maxArtifactChars`. `maxArtifactChars` is allowed because it is a
  pure size gate (review-runner.ts:271-272), not part of any identity.
  **Refused**: `maxContextChars` — it is identity via
  `effectiveAuditUnitChars` in the audit key (audit-reuse.ts:27-30) and the
  envelope windowing budget (review-input.ts:110+); the refusal names this
  reason.
- **Validation**: `validateDef` against the `FrozenReviewSettings` schema in
  `author.schema.json` (the same ranges the settings schema enforces,
  settings.ts:52-62 — one validator, not two), applied to the **merged
  result** (`current frozen settings ⊕ patch`) — the schema requires the
  full object, so a partial patch cannot validate alone. The patch itself
  deep-merges ONLY explicitly provided keys (no schemastery `.default()`
  materialization of absent keys into the patch).
- **Field map** (published for implementers; the inverse of
  `freezeReviewSettings`, review-config.ts:14-27):
  `maxCallsPerRun` ↔ `review-max-calls-per-run`,
  `maxInputTokensPerRun` ↔ `review-max-input-tokens-per-run`,
  `maxOutputTokensPerRun` ↔ `review-max-output-tokens-per-run`,
  `maxOutputTokensPerCall` ↔ `review-max-output-tokens-per-call`,
  `wallMs` ↔ `review-max-wall-ms`, `callTimeoutMs` ↔
  `review-call-timeout-ms`, `concurrency` ↔ `review-concurrency`.
- `contractChanged` is NOT set (§15 contract invalidation does not apply to
  a capacity revision); the head revision bumps through the existing CAS
  machinery (expectedRevision conflict path inherited; in-flight
  admissions that lose the CAS race get REVISION_CONFLICT and retry —
  disclosed).
- Result shape: `{ fieldsChanged: {key: {old, new}}, reuseStatement, contractChanged: false }`.
- **claimsBatchSize revision is reuse-shape-scoped**: it changes the task
  partition `planStage` produces (review-plan.ts:248-269), so claims-stage
  cache keys naturally differ across shapes; records are not invalidated —
  they match only within the same batch shape. The revision response
  discloses this, and delivery/progress may report claims `not-run` after a
  reshape (pinned by test).

### F3.4 Cycle interaction

The cycle ledger persists its budget: a cycle's stored budget is fixed at
cycle creation **except by revision**, and reservations use the cycle's
stored budget. This is an implementation change to the reservation path —
today `reserveCycleCall` receives the caller's snapshot budget
(review-cycle.ts:121-131); it must instead read the cycle's persisted
budget (stored on the cycle's lead request record at admission, inside
`withBudgetLock`). `set-review-settings` updates the LATEST cycle's stored
budget atomically under the same lock — future admissions in that cycle see
the new ceiling; in-flight runs keep their locally frozen `deps.budget`
(the runner never re-reads the cycle budget mid-run). Disclosed behavior;
no other enforcement.

### F3.5 Where the revised settings take effect

- `argument.review` resolves frozen settings from
  `snapshot.contract.reviewSettings` at admission (tools.ts:352) — the
  revision is a head mutation; the next review reads it through the normal
  snapshot read. No read-path change.
- The end-of-run freshness compare (review-runner.ts:443-481) uses the
  semantic contract — a settings revision does NOT make an in-flight run
  `incomplete`.
- The Fix 1 gate and Fix 2 message consume the revised values automatically.
  The Fix 2 refusal message gains option (d): "revise the frozen budget on
  this project (argument.update op set-review-settings) — sources, evidence
  and completed review records are preserved."
- **User-facing surfaces rewritten in this PR**: the `/vwa init` capacity
  footer (commands.ts:261-262 — "cannot be changed after init" becomes
  false once this lands) and the README en+zh freeze lines now name
  `set-review-settings`.

## 3. Tests

- **End-to-end identity pin** (the F3.1 guard): start from a run that
  ended `budget-exhausted` mid-plan (pending work remains — a completed
  review would be refused NOTHING_TO_CONTINUE before reaching any of
  this), revise the budget upward, re-review with `continue` → the pending
  work executes, the completed records are reused (zero-token usage rows),
  no re-dispatch — across semantic stages AND audit (continue-mode audit
  reuse from Fix 1 F1.2). After the continue run completes, delivery and
  progress must also report currentness over the reused records (not just
  the reuse ledger) so a missed comparison site fails loudly.
- **Site-coverage pin**: a set-contract mutation still invalidates all
  semantic reviews (unchanged §15 semantics — the semantic hash changes).
- `claimsBatchSize` revision: same-shape reuse works; cross-shape does not
  match and does not error; delivery reports claims not-run after reshape.
- Refusals: `maxContextChars` patch rejected with the semantic-field reason;
  out-of-range values rejected with schema ranges; unknown fields rejected;
  a set-contract payload carrying `reviewSettings` is explicitly rejected
  (today it is silently overridden, graph.ts:179-180 — with a revision op
  existing, the override becomes an error).
- In-flight: a run admitted before revision completes (not `incomplete`)
  under its frozen local budget; a concurrent admission racing the revision
  gets REVISION_CONFLICT.
- Cycle: admissions after revision in the same cycle use the revised cycle
  budget; a fresh cycle gets the revised snapshot budget.
- Upgrade disclosure: a project with pre-upgrade records does not reuse
  (one-time invalidation, pinned as expected behavior with a comment).
- preset real-boot suite run locally (budget semantics PR rule).

## 4. Risks and mitigations

- **Site-list completeness** is the load-bearing risk (it sank v1). The
  grep regeneration is part of the implementation checklist, and the
  end-to-end identity pin in §3 fails if any site is missed — a missed
  production site fails safe (revision invalidates), a missed comparison
  site fails loudly (records vanish from currentReviews/delivery/progress,
  caught by the pin).
- **One-time invalidation** at upgrade: accepted and disclosed per the
  user's option-B adjudication (money, not correctness).
- **Cycle budget rewrite under the lock**: F3.4 changes the reservation
  path to read the cycle's persisted budget inside `withBudgetLock` (a
  signature/semantics change to `reserveCycleCall`, spelled out above);
  the revision writes under the same lock — no new race surface.
