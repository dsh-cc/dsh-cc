# deepseek-harness 0.1.5-rc.1 Compatibility — Design

- **Status**: reviewed (critic cold-review findings incorporated) — ready for implementation
- **Date**: 2026-09-12 · **Owner**: dsh-cc orchestrator session (worktree `dsh-upgrade-v0.15.0`)
- **Supersedes**: `docs/plans/2026-09-08-harness-0.1.2-rc1-compat.md` (PR #13)
- **Upstream anchor**: npm `@deepseek-ai/dsh` dist-tag `latest` = **0.1.5-rc.1** (`@next` = 0.1.5-rc.2, `@alpha` = 0.1.5-alpha.2), release commit `1ef9c1fa9afbea78c5537bfc8b6d1c27d598798e`.

## 1. Why now

`npm install -g @deepseek-ai/dsh` moved from 0.1.2-rc.1 (our pinned compat target, `a66e4702`)
to 0.1.5-rc.1. Per policy, dsh-cc anchors to the dsh meta-package `latest` tag — this is the
retarget. The work is intentionally small: **the type and test gates are already green against the
0.1.5-rc.1 sibling build** (typecheck clean, 4516 tests passed, 0 failed) — while
`check:publish` is currently **RED (exit 1, ~250 violations)** precisely because the manifests
still floor at 0.1.2 (verified live this session; additional motivation, not a regression).
See §4 for the empirical basis. The remaining work is pin/floor hygiene plus two verified semantic fixes.

## 2. Verified forces

1. **semver floor exclusion (blocking).** node-semver's prerelease-tuple rule:
   `>=0.1.2-rc.1` admits `0.1.2`, `0.1.5`, `0.1.2-rc.2` but **NOT** `0.1.5-rc.1` / `0.1.5-rc.2`
   (verified against semver@7.8.5). Today's default dsh install is `0.1.5-rc.1`, so every
   harness range in dsh-cc currently **rejects the current npm install**:
   - launcher bootstrap gate `packages/launcher/tui/bootstrap.mjs:328`
     (`export const MIN_DSH_VERSION = '0.1.2-rc.1'`) fails the newest dsh at startup today;
   - 306 `>=0.1.2-rc.1` occurrences across 61 `packages/**/package.json` files
     (link: locally; transformed at publish);
   - `pnpm-workspace.yaml:25-26` `minimumReleaseAgeExclude` pins `dsh-timeout@0.1.2-rc.1` /
     `dsh-http-proxy@0.1.2-rc.1` — stale now that the profile pulls 0.1.5 packages
     (http-proxy is newly load-bearing: web-fetch-http routes via
     `installProxyFromEnvironment` at boot since 0.1.5).
2. **resume-pins silent degradation (functional).**
   `packages/subagent/resume-pins/src/plugin.ts:237-243` probes child-session existence via a
   defensively optional-chained `ctx.sessionPersistence.readStoredRevision`. The 0.1.5
   session-persistence face is rewritten to a handle model
   (`create/open/flush/stat/list`); `readStoredRevision` is gone, so the guard is silently
   `undefined` and `sessionExists` is always `false` — the resume gate misjudges. Correct
   replacement at 0.1.5: `stat(id)` → `SessionPersistenceSnapshot | undefined`, where
   `undefined` means not-exists (no throw for missing — `SessionPersistenceNotFoundError`
   only comes from `open`). The old probe survives only on the internal `PersistenceBackend`
   contract, never on the cordis service face.
3. **pin truth.** `.github/workflows/presubmit.yml` `DSH_HARNESS_REF` still pins `a66e4702`;
   `publish.yml` derives from it. CI currently verifies 0.1.2, not 0.1.5 — green CI no longer
   proves anything about the runtime users actually install.
4. **Docs truth.** `README.md:25,27` / `README.zh.md:25,27` state the `>= 0.1.2-rc.1` floor;
   `docs/claude-code-capabilities.yaml:672` (web-fetch entry) cites "upstream rc.1" behavior —
   the DNS-pinning claim is still accurate at 0.1.5-rc.1 **plus** upstream now routes through
   `dsh-http-proxy` when proxy env is set (adds one clarifying clause, no verdict change).

## Revision 1 (2026-09-12, mid-implementation): false-green root-caused, one new item

The §4 "suite green" was a **false green**: the sibling harness checkout had been switched to
`1ef9c1f` but its `lib/` build was stale (built 2026-09-08 on the 0.1.3-alpha line; the old
session-persistence-jsonl lib still exposed `readStoredRevision`, masking the face change).
After rebuilding (`pnpm install --frozen-lockfile && pnpm run build:lib` at `1ef9c1f`, per the
harness-version-line-drift SOP), the real 0.1.5 surface exposed:

- **5.3 confirmed real**: resume-pins probe fix necessary and sufficient (red spec as designed).
- **NEW item 4b — testkit double-mount migration (mechanical, specs only).** At 0.1.5,
  `mountAgentLoopTestDependencies` (agent-loop-testkit) registers `SessionProjectionRegistry`
  itself, so every spec that also calls `ctx.plugin(SessionProjectionRegistry)` fails at boot
  with `service "sessionProjections" has been registered` (236 test failures across
  hooks/interaction/bundle/subagent on first post-rebuild run). Fix: delete the redundant
  mounts in specs that rely on the testkit; production mounts are untouched (agent-loop's
  hard `sessionProjections` inject still requires explicit mounting outside testkit).
  Verification: full suite returns to 0 failures.

Sequencing: 4b lands as its own commit BEFORE the resume-pins green commit. §7 DoD is
otherwise unchanged; DoD-2's "0 failures" now specifically re-proves 4b.

## Revision 2 (2026-09-12): post-rebuild failure taxonomy — four new items

After the lib rebuild (Rev 1) + testkit double-mount sweep (item 4b, done: 236→103), the
remaining 103 failures cluster into four distinct 0.1.5 drifts, each its own commit:

- **item 4c (specs, mechanical) — session header v3 sweep.** Specs building sessions with
  `version: 0` metadata fail `session header version must be 3, got 0` (permission-rules
  cluster: auto-stage/listener-auto-stage/permission-rules/session-allow-integration;
  command-permissions; cc-tui/compaction bridge-adjacent specs). Migrate headers to
  `version: 3` + `isSeeded: false` (validateSessionHeader@0.1.5 contract); prefer
  Session.create through the harness where a helper exists.
- **item 4d (environment) — native addon.** background-Task specs need
  `native/system/packages/darwin-arm64/bin/system.node` (flock); built via
  `pnpm run build:native-system` in the sibling checkout. Environmental; no repo change,
  recorded here so CI's cache key (DSH_HARNESS_REF) covers it.
- **item 4e (test helpers) — persistence face renames.** `boot()` helpers calling
  `persistence.create(...)` / `readStoredRevision(...)` (subagent/task resume-pins.spec,
  cc-shell schedule-bundle, background-composition) must move to the handle face
  (`create(header, options?) → SessionHandle`, `open`, `stat`, `flush`); read tests that
  inspected storage now go through `handle.read` / `stat().revision`.
- **item 4f (specs/src, semantic) — agent/cordis drift cluster**: `agent.followup` no longer
  exists (plugin-hooks-seam specs); `cannot get property "agent" without inject` at
  command-permissions; `agent.ctx` undefined (mechanism-pins); `AgentLoop.create` async at
  cache-trajectory `runner.ts:115` + `testing.ts:43` (the 2 tsc errors). Route root-cause to
  critic before patching: each site needs the 0.1.5 replacement idiom verified in-tree, not
  guessed.

Ordering: 4c → 4e → 4f (each re-runs the suite; count must converge to 0). The resume-pins
green commit (3) lands after 4e since resume-pins.spec boot helpers live in both scopes.
