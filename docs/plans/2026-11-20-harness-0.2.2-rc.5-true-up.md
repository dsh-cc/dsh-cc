### 3.4 S4 — removed `list()` / `listChildren()` / `drainChildren()` (R3)

**3.4.1 Plugin-agent discovery — authoritative snapshot + events.** A purely event-driven index cannot see providers registered before the listener attaches, and production mounts `cc-shell-glue` (which mounts CC plugins on disk and registers their `AgentProvider`s through `mountAgents`) BEFORE `subagent-task` (preset rows `agent.shared.cordis.yml:509` vs `:591`; the catalog's own comment `task/src/catalog.ts:190-194` documents the order); the harness emits `subagent/provider-added` exactly once with no replay (`index.ts:539`). Design:

- Publish a root-realm registry service `ccPluginAgents` (shape: `{ knownIds(): readonly string[] }`, optionally `{ get(id): AgentDefinition | undefined }`) from `compat/cc-plugin-loader` — written at registration time inside `mountAgents` (`agents.ts:276` `subagents.registerProvider(provider)`), maintained by the same disposers, following the existing root-publication idiom (`bundle/cc-shell/src/ccPlugins.ts:137-151`: `root.provide` + adopt-stale-slot + clear-on-unload). This is the authoritative initial snapshot — it exists precisely because the harness service exposes no provider enumeration.
- `PluginAgentIndex` (`subagent/task/src/plugin-agents.ts`): `list()` reads the `ccPluginAgents` service (lazy, every call — same contract as today) and falls back to `seamOverride` for hermetic tests; the existing event listeners in `catalog.ts:188-205` stay for live invalidation (they already brand-guard and seed `brandedIds`; their seed loop switches from `pluginIndex.knownIds()`-via-seam to the service). The listener-then-seed ordering pattern is harness `subagent/tool-subagent/src/index.ts:349-364`.
- Tests: `PluginAgentIndex` fakes provide the `ccPluginAgents` service (or a `seamOverride` carrying the name set) — the provider EVENTS alone can no longer satisfy `PluginAgentIndex` tests after the fold (events only invalidate the catalog listener). The pre-registration scenario (`plugin-agents.spec.ts:89+`) publishes the service in its fake seam; a separate case covers the listener-after-registration order on the catalog side.

**3.4.2 `/agents` + snapshot — `listDescendants`.** The standalone `listChildren(ctx, id, signal)` is NOT barrel-exported from `@deepseek-ai/dsh-subagent`; the service method `ctx.subagents.listDescendants(rootSessionId, signal?)` IS (harness `index.ts:427-429`; entries carry `id`, `mode` (via `KnownSubagentCatalogFields`), `depth`, `path`). Replace the removed service `listChildren` calls in `interaction/command-agents/src/index.ts:73` and `snapshot.ts:80,150` with `listDescendants` filtered to `depth === 1` rows for direct children, wrapped in try/catch: the call throws `SubagentError` (`SUBAGENT_CONTROL_*`) when sessionQuery/projections are absent — degrade to an empty list with the existing `release.ts:232-237` degrade idiom extended to cover service throws (guard the throw, not just seam absence).

**3.4.3 Seam type cleanup.** Drop `list()` and the type-only `listChildren?` from `SubagentsLike` (`task/src/background-start.ts:77,88-96`). Capacity is already the harness pool's job exclusively (`resume-pins/src/live-capacity.ts:3-10,51-63`; `task/tests/tool.spec.ts:1472-1486` pins "no listChildren pre-count") — do NOT introduce any new counting path.

**3.4.4 Release — retained `dispose()` receipts, not `drainDescendants`.** The r1 draft said the drain gate "becomes a no-op"; that is false: `release.ts:223-225` hard-throws `ReleaseFailure('no-drain-seam')` when `drainChildren` is absent — at rc.5 it always is, so `release_agent` and `/agents release` are fully broken. The r2 draft replaced it with `drainDescendants([childAgent])`; that is ALSO wrong and both NO-GO seats proved it: `drainDescendants` accepts only subagent TREE ROOTS (`manager.ts:289-290` filters `this.rootOf(root) === root`), and a spawned child is a MEMBER of its creator's tree (`rootOf` returns the owning root, `manager.ts:509-528`; upstream's own test `continuation.spec.ts:1747-1760` pins the ignored-child behavior, and the upstream upgrade guide `docs/upgrade-guide/v0.2.1-rc.2/subagent-service-methods/guide.md:16` states there is no per-id replacement — per-execution teardown is the activation receipt's `dispose()`). Design:

- New root-realm service `ccContinuableDisposals: { tryDispose(childId: SessionId): Promise<boolean> }`, published by `@dsh-cc/subagent-task` at plugin apply using the existing root-publication idiom (`bundle/cc-shell/src/ccPlugins.ts:137-151`: `root.provide` + adopt-stale-slot + clear-on-unload). `tryDispose` resolves `true` when a receipt was held and its `dispose()` settled, `false` when no receipt exists for the id.
- Registration: one shared helper `startTrackedActivation(seam, spec)` in the task package — calls `startActivation`, registers `childId → activation.dispose` in the service, and removes the entry once `dispose()` has been invoked (successfully or not). Every dsh-cc production lane that starts a CONTINUABLE child uses it: `background-start.ts:332` and `:449`, the fork sentinel `tool.ts:286-291`, and `coordinator/src/index.ts:188` (its workers are parent-delivery continuable). One-shot caller-delivery lanes (ephemeral-dispatch, memory-job, recall-selector, hooks dispatch) self-manage their receipts and do NOT register — the release mode gate refuses them as today.
- `runRelease` Step 5: replace `subagents.drainChildren!(parent, [SessionId(id)])` with a deps-injected `disposals.tryDispose(SessionId(id))` (runRelease takes it through `deps`, like `agents` — it has no ctx). Applies to every drain row (catalog, registry-only, catalog-unreadable × present). When `tryDispose` returns `false` on a row whose registry read says the child is live, return the existing `still-resident` outcome (honest: dsh-cc holds no receipt — a spec covers this branch); when no live agent exists, the existing not-resident paths stand (cold-resume: in-process children do not survive the process).
- Catalog read (Step 1): `listDescendants(SessionId(parent.id), signal)`; a `depth === 1` row is the released id's direct-child evidence; a `depth > 1` hit maps to `not-direct-child` BEFORE any dispose attempt (this reason is now derived from the catalog depth, not parsed from drain error text). The `stale-parent` reason is RETIRED: with an id-keyed dispose there is no parent identity to go stale — its outcome kind, copy, and spec rows are removed in the same commit (public-surface change recorded in §8.5).
- Keep the honored-cancellation checkpoint, `markReleasing`, the observe-timeout race, and the post-read polling semantics unchanged; update `ReleaseFailureReason` copy only where the seam names changed.
- Regression: the release spec matrix (mode gate, tombstone no-op, not-direct-child, registry-only, still-resident-on-no-receipt) re-targets the new seam; add cases for releasing a NAMED direct child, a grandchild id, and a no-receipt live child.
