## 1. Problem

Upstream `@deepseek-ai/dsh` moved its `latest` dist-tag to `0.2.0-rc.2` on 2026-09-29 (`next` converged to the same build; `alpha` is parked at `0.1.7-alpha.2`). dsh-cc's single source of truth for the harness line — `DSH_HARNESS_REF` in `.github/workflows/presubmit.yml:47` — still pins `0.1.7-rc.2`, the published peer floors say `>=0.1.7-rc.2`, and the launcher's bootstrap gate (`packages/launcher/tui/bootstrap.mjs:527`, `MIN_DSH_VERSION`) requires only `0.1.7-rc.2`. Every fresh `npm i -g @deepseek-ai/dsh` therefore pairs dsh-cc with a harness line we have never verified — the unverified-pairing gap from docs/plans/2026-09-25-versioning-and-release-management.md (PR #147, open); filling it by hand is that plan's runbook R4 step 3 executed manually.

This document designs the retarget: what changed upstream, what dsh-cc must touch, in what order, and how each step is verified.

## 4. Design questions

### Q1 — ConfigEditor `configuration()` inherited-view rewrite — is the 0.1.7 migration guard still safe?

The rewrite (boot/config-editor, +16/−2): ids covered by a profile-layer config patch keep the old per-entry `inherited()` computation; all other ids now get `inherited` from the *composed patch layers* (first row wins over `[...layers, patches]`), treating an own key present-with-undefined as an override. The `override:` expression and the `entries()` row set are byte-identical (verified by two independent review lanes).

Why the guard stays correct — argued from source, NOT from the existing tripwire suite (round-1 unanimous finding: `provider-bridge.spec.ts` doubles ConfigEditor, header at spec:27 says so, and the "real provider" fixture doubles it too at :213; my v1 cited 17/17 as integration evidence — retracted):

1. The guard (`packages/ui/tui/src/provider-bridge.ts:115-126`) reads **only `row.override`** in its shared-key comparison (:124); the `inherited` view is never consulted.
2. The `row === undefined` fallback (:121-123, presence-guard on the user section) depends on **which rows `configuration()` yields**, which is `entries()` — unchanged by the diff.
3. The macro-level predicate the 0.1.7 incident established — "treat only a *profile-layer* override as conflict" — is exactly the dimension upstream did not touch.

Changes this amendment makes anyway, because a verification leg that cannot fail for its cited risk is worthless: this PR **adds a real-ConfigEditor integration spec** (`provider-bridge` mounted against the genuinely computed `configuration()` of the linked `@deepseek-ai/dsh-config-editor`, declared per the spec-deps gate) covering the incident-#3 scenario (composite-default row present, profile patch present/absent), and §5.5 makes that spec a permanent member of the retarget battery. The `provider-bridge.ts` comment gains a pointer to this section.

### Q2 — Session/agent-loop recovery semantics (repair.ts rework + ToolCallRecovery in agent-loop)

Behavior change is **live-execution**, not restore-only (codex/grok correction accepted): when a step throws, the agent loop now appends synthesized `tool/result` events for pending calls before `step/end`, via a session-event observer (`agent.ts:328+`); the scheduler contract comment changed correspondingly. dsh-cc consumes the harness agent loop (it forks tools, not the loop), so the change executes under dsh-cc's tool bridge/fork on every failed step.

Decision: absorb as-is. Evidence stack: (a) upstream's own expanded suites (tool-calls.spec.ts +193 incl. pending-settlement cases; resume.spec.ts +69), (b) dsh-cc full `vitest run` against the new line: 6768/6771 with the three failures confined to the documented hooks-cluster load flake (§2.2 row, §5.4 waiver) — its agent-loop-testkit-driven integration suites exercise failure paths through the real loop, (c) §5.8 dogfood watches exactly this surface. A dsh-cc-side synthetic failed-tool integration case is a reasonable follow-up, recorded in §6 R3 — not gated on this PR because the change is upstream-shipped behavior the whole `latest` install base already runs.

### Q3 — user-questions / tool-ask-user timed mode: adopt or ignore?

Corrected claim (three lanes): not "purely additive" — the service's superclass changed (`TypertRemoteService`, installing projection/event handlers at construction), its package gained runtime deps and export subpaths, and `tool-ask-user` gained an opt-in `mode: 'timed'` (default `'legacy'`). dsh-cc's own ask path (`ask_user_question` via tui driver-modal/driver-approvals + the legacy `apply(ctx)` default) compiles clean (tsc) and boots clean (smoke) under the new implementation.

Decision: no adoption in this PR; run on legacy/default shapes, which upstream kept source-compatible. Follow-up candidates (recorded, not scheduled): timed ask for CC parity (product decision, capability-manifest impact), and whether the new projection view should feed TUI state.

### Q4 — Tools fork strategy

Upstream `packages/core/tools` = version line only (independently confirmed). Decision: no rebase. The per-bump protocol stays mandatory: `git diff --stat <old>..<new> -- packages/core/tools` before deciding; record the outcome in the PR (this paragraph is that record for 0.2.0).

### Q5 — New `otel` base row: inherit or disable?

Unconditional row; actual export posture is governed by the (unchanged-id) `session-telemetry-otel` row's `mode: FEEDBACK_ONLY` default. The pre-existing comment "the launchers patch the row disabled" covers the telemetry row; the bare `otel` row (SDK/bootstrap plumbing) has no such note — per review, the FEEDBACK_ONLY rationale does not automatically describe what `otel` itself does, so §5.8 dogfood explicitly names it (`otel` service present, no egress absent user feedback).

Decision: inherit (passthrough), as with all telemetry rows since 0.1.7. Smoke proves resolution in the sibling-built composition; the published-closure check is §5.6. Reversal is a one-row cc-shell patch change, deliberately left out of this PR's diff.

### Q6 — Shape of the change

The compile/boot gates were green and the full suite stood at 6768/6771 (documented hooks-cluster waiver, §5.4) *before* any edit (§2.2) — unlike 0.1.7 there is no expected-red window to manage. Single PR, five commits:

## 5. Verification plan (order matters)

1. **Sibling first**: checkout pinned ref, clean stale dirs, `pnpm install --frozen-lockfile && pnpm run build:lib`; verify `lib/` mtimes fresher than the switch (stale-lib false-green guard).
2. `tsc -b tsconfig.packages.json --force` (incremental-capable checks lie on retargets).
3. `pnpm smoke:profile-boot` (pty-escalated; yml/config drift net; confirm the npm-global fallback notice is absent from the log).
4. Full root `vitest run`. Flake acceptance stays signature-bound (timeout-only + zero AssertionError + untouched files + isolated re-run green), naming the exact files, with the round-1 caveat honored: dependency-drift regressions in "untouched" files are *not* auto-waived — the waiver applies to the documented hooks-cluster load timeouts only; CI presubmit is the final net, and a clean CI run is required for merge either way.
5. The new real-ConfigEditor integration spec (Q1) green, plus the existing `provider-bridge.spec.ts` contract suite.
6. Published closure, in two honestly-scoped legs (review-prompted; both external lanes caught v1/v2 overstating what smoke + check:publish prove):
   (a) **Pre-merge, registry approximation**: scratch-prefix clean install of the user's actual install path against the CURRENTLY PUBLISHED dsh-cc CLI line —
   `npm i -g --prefix /tmp/dsh020-closure @deepseek-ai/dsh@0.2.0-rc.2 dsh-cc-cli-line…` — no, concretely: `npm install --prefix /tmp/dsh020-closure -g @deepseek-ai/dsh@0.2.0-rc.2` then `@dsh-cc/cli@<current published rc>` into the same prefix, pty-boot `dsh-cc` once, assert first frame. This validates the *existing* published chain against the new harness (floors `>=0.1.7-rc.2` and `MIN_DSH_VERSION 0.1.7-rc.2` both admit 0.2.0 — this leg is also the "no surprise breakage for users who haven't waited for us" check). It cannot test THIS branch's artifacts — they are unpublished by definition;
   (b) **Post-publish, exact closure** (new REQUIRED release step this doc adds): immediately after this migration rides the next rc publish and BEFORE announcing it, repeat the same scratch-prefix clean install+boot against the new artifacts and record pass/fail in the release notes; failure → fix-forward or pair-pin the release notes. The smoke script is NOT this leg (it stages workspace copies and pins the sibling CLI at `:64` unless `pool_ok` fails per `:96-100`; nothing in it consumes a tarball).
7. Static gates battery: `check:spec-deps` (whose census doubles as the `>=0.1.7-rc.2` zero-remaining-grep host), `check:deep-imports` (CI-scoped — run locally too), `check:vendor-purity`, `check:size`, README hash pair re-recorded, `check:parity`, `check:capabilities`. (Battery thickened per round-1 review.)
8. Post-merge dogfood week on a real `dsh@0.2.0-rc.2` global install; watch surfaces: Q1 guard (open /provider once, confirm no warn-once conflict log), Q2 (stage a step failure that escapes with outstanding tool calls — the recovery trigger per agent.ts:342-356 and the tool-calls.ts:43-49 scheduler contract — and assert the transcript records synthesized `tool/result` events BEFORE `step/end`), Q3 (legacy ask path), Q5 (`otel` row mounted, no unexpected egress).

## 6. Open items / risks

- **R1 — Behavioral drift without a signal.** Q2/Q3-class changes (upstream behavior shifts with portable types) are verified by upstream's tests + our full suite + dogfood, not by our own targeted tests. Accepted for a retarget; §5.8 names the watch.
- **R2 — Standing composition-coverage gaps** (inherited, unchanged): `packages/preset/cc/tests/composition.spec.ts` has two distinct gates — the drift gate (`:133-142`) HARD-FAILS when no upstream standard-preset anchor resolves (deliberate, G15), while the installed-deployment `@deepseek-ai` resolution check (`:486-491`) warns-and-returns when neither deployment anchor (profile pool, npx cache — `:469-486`) exists. `smoke:profile-boot` IS in `.husky/pre-push:8` (local push gate) but NOT in `.github/workflows/presubmit.yml` — the standing gap is CI-only. Both are recorded for the versioning program (PR #147's dual-leg presubmit would absorb the CI leg).
- **R3 — Failed-tool integration case** (Q2 follow-up): a dsh-cc-side synthetic step-failure test asserting synthesized `tool/result` before `step/end` is cheap and worth adding later; not blocking (upstream tests + dogfood).
- **R4 — Telemetry passthrough is a decision, not an endorsement** (Q5); reversal is a one-row patch change in cc-shell, out of scope here.
- **R5 — Pre-existing stale vitest alias** (`dsh-tool-subagent-report`, predates this migration): flagged for a sweep PR, not fixed here to keep the retarget diff clean.
- **R6 — Claims debt to PR #147**: this manual R4-step-3 closes the 0.2.0-rc.2 gap; the systemic pins.json/watcher machinery stays open. Slices here are forward-compatible with it.
- **R7 — The user-facing README floor and the launcher gate now both say 0.2.0-rc.2**, meaning users older than 0.2.0-rc.2 are deliberately gated out of the next dsh-cc release — intended (floor = verified line), stated here so the release notes say it plainly.
