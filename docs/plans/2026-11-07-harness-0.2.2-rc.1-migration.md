## 1. Goal and non-goals

Bring dsh-cc onto harness 0.2.2-rc.1 with zero behavioral regressions on the CC-compatible surface, same slice discipline as the 0.2.1-rc.5 migration (PR #317). Two r1-identified behavior deltas are accepted explicitly and documented (D5 rest-bucket ordering; truthful `[model changed]` notices under moa) — see §8.

Non-goals: upstream web-app preset rows with no CC-surface overlap (persona/time-context/command-goal/present/plugin-manager/market — explicit non-adoption), settings-fork convergence, credential-priority UI leftover from #317.

### 2.2 Runtime families beyond tsc (all verified against the pin)

### D2 — Tools fork: re-vendor onto 0.2.2-rc.1, re-apply the delta set

**Decision: re-vendor, not an incremental port.** The fork's 6-file `runtime-*` split sits on the wrong side of the upstream executor boundary; an incremental port would re-thread `toolSet`/`when` through every signature and still have to invent the executor contract the boot failure proves is mandatory.

1. **Reset** `packages/core/tools/src/` to the upstream 0.2.2-rc.1 tree (9 files) verbatim, then re-apply the surviving fork-only deltas:
   - `reserve(name)` / `isAdmitted(name, scope)` (consumed by `core/tool-search`, `subagent/task`);
   - `cc-names.ts` (CC↔harness tool-name translation; ~12 consumer src files);
   - `currentToolExecution()` + **the execution-identity async-local instrumentation around tool dispatch** (r3-consolidated, replaces both the r2 waterfall text and D7's batch-wrapper text): upstream's `pipeline.ts:258` `dispatchToolBody` is private and invokes bodies with no hook, so a batch-level wrap around the fork executor's `execute()` does NOT restore per-call identity. The fork hooks the public **`tools/execute` around-dispatch waterfall** (upstream `pipeline.ts:299-301`) — one listener entering the async-local context before and exiting after each call's dispatch. The **tested contract is restated for the new boundary**: identity is active exactly around the call's body dispatch (`pipeline.ts:299-301` wraps `dispatchToolBody`) — which contains the body's own `approval/request` (where permission-rules grant-escalation reads it), but NOT the `prepare()` guards at `:199-213` (`tools/pre-execute`, `checkGuards`), which run outside the wrap. The `current-execution.spec` expectations assert exactly that boundary (body + nested approval, replacing the old body-only assertion), and `grant-execution-binding.spec`'s outside-body rejection keeps passing because `approval/request` fires inside the body call. Consumed by permission-rules grant-escalation;
   - `tool/code-dispatch` + `tool/code-dispatch-start` session events + `KNOWN_SESSION_EVENT_TYPES` registration + the dispatch `meta` writer + the live `tools/code-dispatch-log` cordis event;
   - `run_code` cwd resolution through `ctx.workingDirectory`;
   - json-schema `$schema`-dialect annotation tolerance + the `json-schema-value.ts` validator extraction;
   - `'code'`/`'both'` presentation — re-expressed as the fork executor (D7).
   - Already absorbed upstream (do NOT re-apply): nested `presentationMeta` (upstream `pipeline.ts:550-557` identical); the `scheduler.ts` `TOOL_RUNTIME_SCHEDULER` shim (symbol deleted; delete the shim and `tests/scheduler-symbol.spec.ts`).
2. **Consumers**: `presentAs` is deleted upstream with no dsh-cc src consumers; the `code-mode.spec.ts` `presentAs` cases are re-expressed against the executor's `describe`/`sections` (asserting the same model-facing surface), not dropped silently. `defineContentToolFixture` imports → `@deepseek-ai/dsh-tool-testkit` (new devDep in `cache-trajectory`, `token-efficiency`, and every spec file's owning package; check-spec-deps gate). 3. **`view(scope).restrictableNames`** (upstream `view` private, no public equivalent): keep a minimal public fork-side accessor with a drift-gate allowance entry; consumers: `subagent/task/tool.ts`, `resume-pins` (gate + plugin), `mcp-client` defer specs, `tool-schema-gate.spec`.

### D3 — Model selection: `AgentModel` at entry-point admission seams

Upstream final semantics (all verified): `Agent.model` (`AgentModel`) — `current()` (recorded pending/lastUsed, else creation options incl. options-carried `reasoningEffort`), `select()` (idempotent durable append); selection read once per step at `preStep` start; `agent/request` step-fatal for provider/model/effort; prompt variables written by agent-loop from the frozen `AssembleContext.modelSelection`; `installModelSelection(agentCtx)` (1 arg) installs the switch-notice listener; **there is no in-process pre-preparation waterfall** (R5), so selection mutation belongs to **entry points** — upstream's own driver/SDK/session-controller/acp all call `agent.model.select()` at admission/config time.

**dsh-cc follows the same architecture: routing becomes an entry-point-level pre-admission step.**

1. **TUI driver** — file set (complete, r2-revised): `driver.ts`, `driver-ctx.ts`, `driver-agent.ts` (`seedDefaultModel`), `driver-pickers.ts` (`applyModelSwitch` :98-111, `/effort` :199-226), `driver-run-local.ts` (typed `/effort` writes at :277,:300; `applyModelSwitch` call at :256), `driver-sessions.ts` (:310-322 rebind/reseed), `driver-hud.ts` (read), `onboarding.ts`, `statusline-wiring.ts`, and the selection adapters `model-cycling.ts` / `model-cycling-binding.ts`, `provider-command.ts`, `provider-detail.ts`. All `selection.current` reads → `agent.model.current()`; writes → `agent.model.select()`; `installModelSelectionWithSanitizer(agentCtx)` → 1-arg `installModelSelection` + sanitizer. The `/model` and `/effort` paths also notify moa via `noteUserSelection` (updating `userBaseSelection`, per D3.2 provenance). **Reset semantics**: `/model` reset re-selects the boot pair captured at driver start (creation options; when the deployment default resolves asynchronously, capture it after the first `current()` resolution — driver-sessions already has that rebind hook). **Precedence**: persisted selection (`modelSelection.lastUsed`) wins over reseeded creation options on resume (upstream's own resume behavior via `AgentModel.current()`); explicit `/model`/`/effort` selects override; reseed only ever selects the boot pair when no durable selection exists.
2. **moa router** (`router.ts`) — the tier rewrite moves to **pre-admission classification**:
   - New exported seam: `routeBeforeAdmission(agent, opening: UserMessage): Promise<void>` — side-effect-free when disarmed. The gate (spelled inline; it is the moa design's §5.3 gate, from `docs/plans/…-moa-cascade-routing`): route only when moa is enabled AND armed AND validation passed AND the agent is the root (not a subagent) AND `opening.source.kind === 'user'` (genuine user turn; non-user sources — `cc-workflow-completion`, `moa-escalation`, notices — never classify). Classifies the opening, and calls `agent.model.select(tierSelection)` — all **before** `agent.followup(...)`, i.e. before the inbox append, driver wake, and the step's `model.current()` read. This is the only seam where an awaited async classification can precede preparation (R5 rules out every in-process waterfall).
   - **Integration rule (r3-revised — every followup, not just dispatchQueued)**: every dsh-cc entry point that admits a user turn MUST await `routeBeforeAdmission` on the exact `UserMessage` it passes to `agent.followup`. Enumerated call sites (grep-verified, re-verified in S4 with a `followup(` grep over `packages/`):
     - TUI idle submit — `driver-queue.ts:289` (calls `followup` directly; route BEFORE that call, not via `dispatchQueued` which serves only the queued-chip flush and zombie re-dispatch);
     - TUI queued-chip flush — `driver-queue.ts:141` (`pending.map(dispatchQueued)`) AND the queued-submit loop at `:277` (r3: same `dispatchQueued(..., 'followup')` shape) AND zombie re-dispatch at `:177`: **every batch form serializes** — classify the batch's FIRST entry only (all queued chips open one turn; later entries are same-turn continuations) and await it before dispatching the batch;
     - plugin/slash command expansions — `cc-plugin-loader/src/commands.ts:317`, `command-init`, `tool-workflow/src/commands.ts:129` (these expand to `source.kind: 'user'` prompts; classifying them is correct — they are genuine turn openings — the miss would be skipping the helper);
     - `tool-workflow/src/registry.ts:359` — a `cc-workflow-completion` followup: **routed through the helper but excluded by the gate** (non-`user` source never classifies; enumerated here so the S4 grep closes cleanly);
     - the judge's escalation followup (`judge.ts:349`) — NOT routed through the helper by design: the escalation bullet specifies select-then-followup directly (enumerated here so the S4 `followup(` grep closes);
     - ACP admission — the vendored `cc-acp` prompt path (D4).
     Headless/SDK entry points: unrouted — documented follow-up issue.
   - **Escalation**: `judge.ts`'s escalation path calls `agent.model.select(toTier)` immediately before `snap.agent.followup(...)` (the typed retry row keeps `MOA_ESCALATION_KIND` provenance; the never-reclassify-a-retry contract is preserved by construction — the judge selects the tier it already computed).
     - **Classification miss = re-select `userBaseSelection`** (the model's `FailOpenServe` serves the user/base pair, and `UserTurn` resets `tier`; merely skipping the select would leave the previous turn's durable tier in force).
   - **`withTier` is deleted**; its effort re-validation (carried effort supported by the tier model, warn-once degrade) moves into the tier-`ModelSelection` computation inside `routeBeforeAdmission`.
   - **Provenance-aware arming (r3-final — explicit signals, not pair inference)**: pair-equality inference is replaced by **explicit write notifications**:
     - moa exports `noteMoaSelection(pair)` (called by the router and the judge's escalation select — updates `lastMoaSelection`, never disarms) and `noteUserSelection(pair)` (called by the driver's `/model` AND `/effort` write paths — updates `userBaseSelection`, disarms moa, and **re-arms when the pair equals the boot pair** — the model's `ModelSwitchBack` transition). The pre-step observation (`observeLiveSelection`) becomes a **tripwire only**: a non-moa, non-boot pair reaching a request without a preceding `noteUserSelection` is a bug and fails the sanitizer spec (r3: observation-based arming can let admission routing overwrite an explicit user choice before disarming).
     - This dissolves the r2 same-tier ambiguity by construction (the user's `/model` write notifies regardless of the pair value), and `/effort` writes carry the current pair + effort into `userBaseSelection` (r3: stale effort on FailOpenServe restore).
     - **Sidecar**: the routing.jsonl sidecar gains a third row kind `user-select` (written by the driver's `/model`/`/effort` paths). Resume rehydration: read the LAST row of any kind and **freshness-check it against the session's durable `model/selection` state** — the sidecar row is authoritative only when its implied pair matches the durable `lastUsed`/`pending` pair (a stale `route`/`escalate` row after an unlogged user write fails the check ⇒ conservative fallback); `route`/`escalate` ⇒ rehydrate `lastMoaSelection` (armed); `user-select` ⇒ rehydrate `userBaseSelection` and set armed = (that pair equals the boot pair), mirroring `noteUserSelection`'s re-arm semantics; missing file or failed freshness check ⇒ unarmed-until-boot-pair. A rehydrated `user-select` row counts as the preceding `noteUserSelection` for tripwire purposes (a `ModelSwitchBack` survives restart). **Crash window** (durable `model/selection` committed but the sidecar row not yet written — judge.ts logs after admission): rehydration falls back to the conservative unarmed-until-boot-pair state; documented and covered by the S4 crash/resume probe.
   - **Sanitizer** (`sanitizer.ts`): the frozen pair is `payload.modelSelection` of `agent/pre-step`. Notices are now truthful by construction (moa's select IS the step selection); the drop rule retires. Keep: (a) the live-selection publisher (feeding `observeLiveSelection`, now provenance-filtered per the arming rule above), (b) a spec tripwire asserting no phantom `model-selection` notice appears while armed. **Corollary (accepted delta)**: tier switches now emit truthful `[model changed]` notices — the effective-model-truth program's intended end state; moa spec expectations updated to match.
   - **Spec/acceptance (S4 gate)**: pty live session asserting (i) `routing.jsonl` row for a turn and the same turn's first request config carrying the tier model; (ii) `/model` mid-session switch disarms moa; (iii) judge escalation selects the escalated tier before its followup; (iv) resume rehydrates arming from the sidecar.
3. **D3.5 — resume-pins** (`plugin.ts:425-435`, `overlay.ts`): the request-time provider/model/effort rewrite is deleted. At child resume/spawn, the pinned tuple is applied via `agent.model.select(pinnedTuple)` in the spawn/resume preparation path (before the first step; the pin store is read there anyway). `maxTokens` stays on `agent/request` (legal sampling control) or moves to options. S4 probe first: verify whether the resumed child's `AgentOptions` already carry the pinned tuple (making the select redundant-but-harmless); the pin-blocked fail-closed throw (`PinBlockedError`) moves to the pre-spawn gate (it must still fail visibly before any model call).
4. **D3.6 — cc-model-aliases stamped-effort overlay** (`service.ts:105-110`): `AgentModel.current()` now honors options-carried `reasoningEffort` (`model-selection.ts:106-108`), which is the overlay's entire purpose (defending the alias effort against a restored parent seed). Probe in S4: a fork-seed child whose parent carries an explicit effort keeps the alias-stamped options effort. Expected outcome: the overlay becomes a no-op → delete it with a regression spec proving options-effort survives; if the probe shows restoration still occurs, apply `agent.model.select(stamped)` in the spawn path instead.
5. **cc-acp model-control**: re-vendor (D4).

### D5 — Tool ordering: `systemPrompt.toolOrder` config + accepted rest-bucket delta

Upstream owns ordering: `orderTools(collected, toolOrder, knownNames)` canonicalizes **before** the assemble waterfall; the waterfall receives no tool array; providers cannot preserve order. Without `toolOrder`: full lexicographic sort per assembly. With `toolOrder: [names…, '<unlisted-tools>']`: listed names render in the configured order; the rest bucket is **re-sorted lexicographically on every assembly**.

**Decision**:
1. Retire `packages/core/tool-append-order` (its seam no longer exists). The `appendStable` helper + per-scope memory move into the fork's test-support surface (the ordering spec survives as a documented contract of the past).
2. Configure `toolOrder` by restating the **host** `system-prompt` row at the **top level of `cc-shell/cordis.patch.yml`** (r2 fold, cross-seat: `toolOrder` is constructor state on the single host `SystemPrompt` service — `agent-loop/src/index.ts:471` assembles on `runtime.ctx` — so an agent preset cannot mount or replace it; a plain same-id top-level restate — NO `disabled: true`, which would unload the host SystemPrompt service; unlike the `tools`/`tools-cc` swap this is the same package, so a restated row with config overrides the base row's config). The restatement carries the base row's `personaPrefix` and every other base field verbatim, plus `toolOrder`: the always-registered CC catalog in a **checked-in captured order artifact** (r2 fold: the retired plugin's fixtures contain synthetic names, not the real catalog — S5 captures the real always-registered emission order from a live boot — the frozen list is checked into the repo as a spec fixture, the source of truth for the yml list), terminated by `<unlisted-tools>`. Only always-registered names may be listed (a listed name with no registered tool rejects every assemble; known-but-restricted absent names are tolerated — conditionally inactive tools like `exit_plan_mode` must therefore sit in the rest bucket, not the list, unless they are registered unconditionally).
3. **Accepted behavior delta (explicit, r1 fold)**: newly activated unlisted tools insert lexicographically into the rest bucket — an activation of a name sorting before an established unlisted tool shifts that tool's position (the old plugin appended at the tail). The static-catalog prefix — the dominant cache-stability surface — is preserved exactly. The Item 6 L0 sentinel e2e is updated to assert (a) the static prefix is byte-stable across activations and (b) rest-bucket ordering follows lexicographic insertion; the capability manifest documents the delta.
